# Solve 단계 아키텍처 비교 — 에이전트 위임 vs API 직접 호출

> 작성: 2026-09-10. 두 방식의 트레이드오프를 비교해 구현 방향을 결정하기 위한 설계 문서.

---

## 1. 두 방식의 정의

### 방식 A: 헤드리스 에이전트 위임 (현재 구현, `src/solve.js`)

```
github issue ──▶ prompt ──▶ claude -p (cwd=repoDir)
                              │
                              ├─ Read/Glob/Grep  (스스로 탐색)
                              ├─ Edit/Write      (직접 파일 수정)
                              ├─ Bash(npm test)  (테스트 실행)
                              └─ 결과 텍스트 반환
```

- `execFile(config.claudeBin, args, { cwd: repoDir })` 로 타겟 레포 디렉터리에서 헤드리스 Claude 실행
- 에이전트가 **도구를 직접 사용**해 로컬 파일을 탐색·수정·테스트
- 코드를 API로 주고받지 않음 — 파일 시스템을 직접 조작
- `--allowed-tools` / `--disallowed-tools`로 권한 통제

### 방식 B: API 직접 호출 + 전체 코드 덮어쓰기 (사용자 묘사)

```
로컬 파일 읽기 ──▶ 텍스트 묶음 ──▶ Gemini/GLM API
                                   │
                                   └─ "수정된 전체 코드" 응답
                                       │
                   로컬 파일 덮어쓰기 ◀┘
```

- 레포 파일들을 읽어 텍스트로 직렬화 → LLM API에 전송
- "수정된 전체 코드를 반환해" 요청 → 응답 텍스트로 로컬 파일 덮어쓰기
- 별도 런타임(claude -p) 없이 순수 API 호출

---

## 2. 트레이드오프 비교

| 차원 | A. 에이전트 위임 (현재) | B. API 직접 호출 |
|------|------------------------|------------------|
| **토큰 효율** | 높음 — 필요한 파일만 Read, Edit으로 부분 수정 | 낮음 — 관련 파일 전체를 컨텍스트에 올려야 |
| **토큰 초과 위험** | 낮음 — 에이전트가 컨텍스트 관리 | 높음 — 레포가 크면 즉시 초과. **파일 필터링 로직 필수** |
| **수정 정확도** | 높음 — Edit으로 정확한 부분만 변경 | 낮음 — LLM이 파일 전체를 재생산해야 → 누락·왜곡·들여쓰기 붕괴 위험 |
| **테스트 실행** | ✅ 가능 — `npm test` 직접 실행 후 결과 보고 | ❌ 불가 — 코드만 주고받음. 테스트 결과를 모름 |
| **자율 탐색** | ✅ Glob/Grep으로 관련 파일 스스로 발견 | ❌ 미리 어떤 파일을 보낼지 호출자가 결정해야 |
| **결정론** | 낮음 — 같은 입력에 다른 결과 가능 | 높음 — 입력→출력이 명확히 로깅됨 (temperature=0 시) |
| **비용 예측** | 어려움 — 에이전트 루프가 여러 번 API 호출 | 쉬움 — 입력+출력 토큰으로 명확 |
| **디버깅** | 어려움 — 트랜스크립트 분석 필요 | 쉬움 — 요청/응답 텍스트가 전부 |
| **런타임 의존성** | `claude -p` 런타임, 도구 화이트리스트, 분류기 의존 | 순수 API 호출. 모델 자유 (Gemini/GLM/어떤 API든) |
| **보안** | 에이전트가 로컬에서 도구 실행 → 권한 통제 필요 (`--disallowed-tools`로 해결됨) | 파일 읽기/쓰기만 — 실행 권한 불필요. 샌드박스 관점에선 더 단순 |
| **멀티 파일 일관성** | 에이전트가 전체 맥락 유지하며 다중 수정 | 파일별 독립 응답 → 파일 간 일관성 깨질 수 있음 |
| **이미 검증됨?** | ✅ 4차 e2e 통과 (status.md 5절) | ❌ 미구현 |

## 3. 핵심 엔지니어링 포인트 — "파일 필터링 / 토큰 관리"

사용자가 짚은 이 포인트는 **방식 B에서만 발생하는 문제**다.

### 방식 B의 필터링 부담 (직접 구현해야 함)
```
어떤 파일을 보낼 것인가?
- node_modules/, .git/, dist/ 제외          ← 디렉터리 필터
- .js/.ts/.jsx/.py 등 소스만                ← 확장자 필터
- 파일 크기 상한 (예: 50KB 초과는 제외)      ← 크기 필터
- 이슈 본문에 언급된 파일 우선               ← 관련성 필터 (가장 어려움)
- 총 토큰 예산 계산 → 초과 시 더 잘라내기    ← 토큰 카운팅
```
- "관련 파일 우선" 단계가 핵심 난제: 이슈가 `auth/login.js` 언급하면 그 파일과 의존성 트리를 찾아야 → 정적 분석 또는 휴리스틱 필요
- 토큰 카운팅: 각 모델의 토크나이저로 정확히 계산해야 초과 방지

### 방식 A의 필터링 부담 (에이전트에 위임)
- 에이전트가 Glob(`**/*.js`)/Grep으로 **스스로** 관련 파일을 찾고 필요한 것만 Read
- 호출자(solve.js)는 필터링 로직을 짤 필요 없음 — 프롬프트에 "코드 구조를 분석하라"고만 지시
- 토큰 예산? 에이전트의 컨텍스트 창이 알아서 관리. 너무 큰 레포면 에이전트가 자체적으로 분할 탐색
- 단점: 에이전트가 "어떤 파일이 관련 있는지" 판단을 잘못하면 → 검증 불가 (방식 B는 호출자가 명시적으로 선택하므로 제어 가능)

---

## 4. 보안 관점 — 의외로 방식 B가 더 단순

방식 A는 에이전트가 로컬에서 Bash 등을 실행할 수 있어 권한 통제가 복잡하다 (`--disallowed-tools`로 `git push`/`gh pr` 하드차단 — status.md 3.8절). 프롬프트 인젝션 방어도 필요했다 (status.md 3.9절).

방식 B는 파일 읽기 → API → 파일 쓰기만 하므로 **실행 권한이 아예 없다**. 샌드박스 관점에선 공격 면적이 작다. 다만 "응답으로 받은 코드를 덮어쓰기"할 때 악성 코드가 파일에 쓰일 수 있으니, 쓰기 전 경로 검증(escape 차단, workspace 내부만)은 여전히 필요.

---

## 5. 결론 — 방식 A 유지 권장, 단 이유를 명확히

방식 A(현재 구현)를 유지하는 것을 권장한다. 근거:

1. **테스트 실행 가능**이 결정적 — 방식 B는 `npm test`를 돌릴 수 없어 "수정이 실제로 작동하는지"를 검증 못 함. 이 프로젝트의 핵심 가치(버그 수정 + 검증)가 무너짐.
2. **이미 4차 e2e로 검증됨** — 방식 B는 미구현이라 0부터. 검증 비용이 든다.
3. **토큰 효율** — 방식 B의 필터링 로직은 복잡하고("관련 파일 우선" 단계가 특히 어려움), 이걸 잘못 짜면 토큰 초과로 아예 동작 안 함. 방식 A는 이걸 에이전트에 위임.

다만 방식 A의 약점도 인지:
- **비결정론** → 같은 이슈를 두 번 돌리면 다른 결과. 면접 데모 시 재현성 걱정.
- **비용 예측 어려움** → 에이전트가 API를 여러 번 호출. 비용 모니터링 필요.
- **인프라 의존** → `claude -p` 런타임 + 분류기(gemma4:26b) 가용성에 좌우됨 (status.md 3.7절).

이 약점을 방식 B가 커버하긴 하지만, "테스트 불가"라는 방식 B의 치명적 단점을 감수할 만큼은 아니다.

### 방식 A 유지 시 남길 보강 (선택)
- `solve.js`에 "에이전트가 컨텍스트/토큰을 어떻게 관리하는지" 주석 보강 (방식 B의 필터링 문제가 왜 여기선 자동 해결되는지 문서화)
- 비결정론 완화: `--output-format json` + 트랜스크립트 저장으로 재현성 확보 (이미 json은 있음)

### 방식 B로 가야만 하는 경우
- `claude -p` 런타임을 쓸 수 없는 환경 (순수 API만 허용)
- 테스트 실행이 불가능한 레포 (테스트 스크립트 자체가 없음) — 그럼 방식 B의 단점이 희석
- 비용을 엄격히 통제해야 하는 배치 작업
